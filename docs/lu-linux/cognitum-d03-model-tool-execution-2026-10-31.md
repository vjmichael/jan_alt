# Lu Linux ↔ Cognitum D03 — Conversation-Bound Model Tool Invocation

**Date:** 2026-10-31  
**Repository:** `vjmichael/jan_alt`  
**Development baseline:** Local reconstructed D02 Lu-Linux environment (pinned Lu source `68eab79e2799c02cec8949993cebd64215f00559`, L16, P0, Cognitum D01/D02 overlays).  
**Disposition:** **D03 experimental developer gate PASSED** for one real model-originated Cognitum tool turn and fail-closed authority negative. **Production / kernel containment: NOT ACCEPTED.**  
**Primary goal:** Cognitum augments the model; it does not replace the model. Keep Windows Lu alpha and the unrelated Cognitum repo untouched.

## 1. What changed in isolated local source

- Added `lu-core/src/cognitum_model_tool.rs`, exposing only `lu_cognitum_rational`, mapped to fixed native ID `lu.cognitum.dev_rational`, with **`ToolEffect::ExecuteCode`**. It is not silently misclassified as a read-only tool. Input and result use the pinned Cognitum `CalculateRationalRequest` / `CalculateRationalResult` Protobuf domain messages.
- Added `lu-core/src/cognitum_dev_approval.rs`, a private SQLite journal with one-use grants keyed to host-minted turn UUID + persisted conversation + USER message + fixed worker digest. An approval expires after five minutes and is atomically consumed; expiration, replay and cross-turn substitutions fail closed.
- The existing development socket `start_turn` accepts **only** the literal operator-supplied `cognitum_dev_approve: "single_turn_execute"`, only when the host started with `LU_COGNITUM_D03_ENABLE=1` and `lu-cognitum-dev-native` enabled. Caller-supplied conversation/task IDs, worker paths, Python or argv are denied. The socket remains owner-private, with a process-rotated secret.
- Lu re-attests the persisted USER turn and active GGUF session, then consumes the approval. **Only then** does the host register the fixed model-visible schema, open the real `ConversationAuthority` task, and issue the matching scoped `PolicyEngine` execute grant. The tool code runs via `NativeToolRegistry::dispatch_bound`, not via the D02 direct smoke method.
- Calls are generated by the LLM as data, validated by the model JSON boundary and Protobuf codec. Model output cannot issue approvals or set tool/root/executable/hash/scope. Lu hosts the immutable call origin. On task revocation the existing Lu authority denies further calls. Cancellation is passed to the worker's bounded child-process loop; the process is killed/reaped on unsuccessful paths.
- Existing read-only native chat and developer direct-worker smoke paths remain available without any D03 grant. D03 is deliberately **Linux developer-feature only**, not a new production extension installer or OS sandbox.

## 3. End-to-end evidence

**Tool test:** `9/14 + 5/21` = **`37/42`** (exact independent rational reference). The model was **Qwen2.5 0.5B Q2_K**, CPU backend, running inside the actual local Lu Linux desktop process with the Cognitum D03 feature enabled.

### Initially different prompt wording (diagnostic example, not a controlled benchmark)

- **Without approval:** model independently gave `19/21` (wrong), `toolCalls = 0`, `modelGenerations = 1`.
- **With approval and a more explicit JSON tool instruction:** model returned `37/42` (correct), `toolCalls = 1`, `modelGenerations = 2`.
- Because the prompts differ, this is a development demonstration **not** a matched WITH/WITHOUT performance study.

### Follow-up: byte-identical user prompt, with and without grant

The **same prompt** instructing the model to request the `lu_cognitum_rational` function was submitted in two separate Lu conversations. The only deliberate control change was the host-issued one-turn approval:

- **Without approval:** model produced `{"kind":"tool","name":"lu_cognitum_rational","arguments":{"expression":"9/14 + 5/21"}}`, but the Lu model boundary rejected it as `Catalog(UnknownTool("lu_cognitum_rational"))`. Lu marked the turn failed; no authorized tool dispatch occurred.
- **With approval:** the model produced the **same tool request**. Lu accepted the authorized native call, Cognitum computed `37/42`, Lu supplied a typed tool-result feedback frame, then a second model generation returned `The result of the computation is 37/42.` The turn completed with `toolCalls = 1`, `modelGenerations = 2` and trace ref `bee7adb87009475d8bbd5a061a5e22d7`.

The private SQLite `lu_model_boundary_audit` verifies, in order: persisted `USER_REQUEST` → actual model-authored `MODEL_OUTPUT` tool envelope → parsed tool candidate → structured `TOOL_FEEDBACK` containing `ok:true`, `value:"37/42"`, `luConversationAuthorized:true`, `kernelConfined:false`, `productionAdmission:false` → second `MODEL_OUTPUT` → `FINAL_ANSWER`. The unapproved branch records a `REJECTED` unknown tool. No claim is made that an arbitrary instruction can force a model to call a tool; another approved run answered directly with zero calls.

This is **genuine live Lu model-to-Cognitum integration**, unlike D02's operator-only direct fixed-worker call. It does not establish statistically significant accuracy improvement; Qwen sampling, system prompt, turn history and model/version must be standardized for benchmarking.

## 4. Scope / assurance / risks

- **Authorization:** In this lab, the socket holder is an authenticated local **operator**, whose explicit approval for a new durable USER turn is persisted and consumed once. This is **not** a production UI approval/ownership/authentication system. The model cannot mint this approval and cannot choose its turn IDs.
- **Worker identity:** SHA-256 pins the worker source file (`f547294522d0b4416bdce76010ca273571ff4820f53f2e2d377ca1fcb1f9c507`). Other Python dependencies and the complete execution environment are **not** independently attested or signed.
- **External code:** Although the *operation* is fixed rational math, the worker starts a Python interpreter; therefore `ExecuteCode` is the only honest effect. No read-only exemption is used.
- **Containment:** Worker result explicitly reports **`kernelConfined=false`**, **`productionAdmission=false`**. D03 does not prove hostile descendants are reaped across crashes, read-only cgroup2, watchkeeper reboot, or parent death. The Cognitum P46 lifecycle track and Lu Windows Job Object / Linux cgroup supervision must not be conflated with D03.
- **Cancellation:** Pre-cancelled worker admission is tested; cooperative cancellation is checked in the worker wait loop and kills/reaps the fixed child on errors. Live cancellation during a long worker operation / process-tree cleanup remains untested.
- **Approval journal security:** Owner-private root and ordinary file/symlink checks are implemented, but this experimental store is not the fully authenticated signed-CE grant subsystem; same-user path races and malicious OS actors need a separate hardening review.
- **No user environment changes:** All GUI launches used a disposable local profile, optional Xvfb and WebKit sandbox disablement solely for this container. Those unsafe GUI flags **must never** ship in release builds. No release/main/Windows-alpha source was altered.
